# 代码审查请求：bot-mindscape

## 你的角色

你是一位资深 Python 后端工程师，正在审查一个即将开源的项目。
请**严格但务实**：找出真问题，不要为凑数挑风格毛病。

## 项目背景

**bot-mindscape** 是一个「给群聊 AI bot 增强能力」的框架，目标运行环境是各种 bot 框架
（主要是 AstrBot，也考虑 NoneBot2）。它的核心理念是解决三个痛点：

1. **金鱼记忆** —— bot 清一次历史就失忆 → 用独立的 Markdown 长记忆文件 + 滑动窗口注入
2. **文字机器** —— bot 不会发表情包 → 视觉模型自动采集契合人设的图 + 概率强制配图
3. **机械出戏** —— 报错外泄暴露 AI 身份 → 发送前拦截所有错误文本

## 代码结构

```
plugins/                     各功能模块（AstrBot 插件形式，但尽量不依赖框架特有 API）
  mindscape_config.py        共享配置读取（YAML）
  mindscape_guard.py         报错拦截（纯函数 is_error_text + 钩子）
  mindscape_memory.py        记忆注入（read_recent / read_people + 钩子）
  mindscape_recall.py        检索工具（score_line / search_diary + LLM tool）
  mindscape_diary.py         日记生成（读 SQLite 消息库 → LLM 提炼 → 写 Markdown）
  mindscape_stickers.py      图片采集（视觉判断 + 分类入库）
  mindscape_sticker_use.py   表情调度（选图 + 强制配图 + 斗图队形）
  mindscape_format.py        输出规范化（压平多行）
  mindscape_janitor.py       会话清理（防历史膨胀）
scripts/
  config_gui.py              tkinter 配置器
  web_ui.py                  标准库 http.server 管理台
  import_stickers.py         多源图库导入

patches/astrbot/             唤醒层补丁（必须在框架层实现，故为补丁形式）
```

## 请重点审查这几个方面

### A. 正确性（最重要）

- **逻辑错误**：条件判断、边界情况、循环退出条件
- **异步问题**：`async`/`await` 使用是否正确，有没有阻塞事件循环的操作
- **状态污染**：模块级变量、实例变量在多事件并发下是否安全
- **正则表达式**：是否可能灾难性回溯（ReDoS）

### B. 健壮性

- **异常处理**：有没有「吞掉异常但用户完全无感知」的地方
- **超时**：所有网络请求（httpx / urllib）是否都设了超时
- **资源泄漏**：文件句柄、数据库连接是否都关闭了
- **失败降级**：配置读取失败、API 失败时，会不会导致 bot 整体不可用

### C. 安全

- **路径遍历**：`web_ui.py` 的 `/img/<filename>` 接口，`os.path.basename` 是否足够
- **任意文件写入**：`web_ui.py` 的配置保存接口
- **注入**：SQL 拼接（`mindscape_janitor.py` 的表名/字段名来自配置，是否有风险）
- **敏感信息**：有没有可能把 API key 写进日志

### D. 兼容性

- 代码假设了「bot 框架的哪些行为」？这些假设合理吗？
- `mindscape_sticker_use.py` 和 `mindscape_stickers.py` 里对 `event` 参数的处理方式是否脆弱
  （注释提到：框架可能把插件类绑在第一个参数，所以从 `args` 里找真 event）

### E. 一致性与可维护性

- 文档描述的字段名 / 行为，和代码实现是否一致
- 有没有重复代码可以合并
- 命名是否清晰

## 请不要报告以下内容（已知且有意为之）

1. **唤醒层是补丁而非插件** —— 这是技术限制（判定发生在框架的消息分发阶段，比插件更早）
2. **没有 pytest 单元测试框架** —— 项目刻意只用最简的自检脚本（`run_selfcheck.py`），不引入 pytest
3. **没有用向量检索** —— 目标环境可能只有 2GB 内存，加载 embedding 模型不现实
4. **tkinter GUI 比较朴素** —— 零依赖是刻意选择
5. **配置项很多** —— 这是「开箱可调」的设计目标
